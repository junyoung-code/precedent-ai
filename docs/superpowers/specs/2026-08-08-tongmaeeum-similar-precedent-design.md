# 통신매체이용음란 유사 판례 탐색 서비스 설계

- 작성일: 2026-08-08
- 상태: 사용자 승인 완료, [구현 계획 작성 완료](../plans/2026-08-08-tongmaeeum-similar-precedent-mvp.md)
- 대상: 비공개 프로토타입

## 1. 제품 목표

사용자가 통신매체이용음란 관련 사건을 자유롭게 설명하고 대화 캡처를 첨부하면, 공개된 공식 판례 중 사실관계가 비슷한 판례를 찾아 다음 정보를 제공한다.

- 사실관계 유사도
- 닮은 점과 다른 점
- 판례에서 중요하게 본 부분의 쉬운 요약
- 법원, 사건번호, 선고일
- 국가법령정보센터 등 공식 원문 링크
- 검색에 사용한 판례 데이터의 실제 범위

이 서비스는 판결 예측기나 법률 자문 서비스가 아니다. 고소 가능 여부, 범죄 성립 여부, 유무죄, 처벌 수위, 승소 확률을 판단하거나 예측하지 않는다. 결과의 숫자는 오직 입력 사례와 공개 판례 사이의 사실관계 유사도를 뜻한다.

## 2. 배경과 제품 원칙

통신매체이용음란 사건은 표현 한 문장만으로 비교하기 어렵다. 당사자 관계, 전송 경위, 전달 매체, 반복 여부, 상대방 특정 방식 등 맥락이 중요하므로 자유 서술과 구조화 질문을 함께 사용한다.

제품은 다음 원칙을 지킨다.

1. **실재하는 판례만 반환한다.** 공식 원문과 메타데이터가 검증되지 않은 사건은 화면에 표시하지 않는다.
2. **법적 결론을 내리지 않는다.** 유사도와 유죄·고소 가능성을 명확히 구분한다.
3. **검색 범위를 숨기지 않는다.** “모든 판례”라고 표현하지 않고 실제 비교한 판례 수와 데이터 출처를 표시한다.
4. **요약보다 원문을 우선한다.** 모든 요약에 공식 원문 링크와 근거 문단을 연결한다.
5. **민감정보를 남기지 않는다.** 회원가입 없이 일회성으로 분석하고 원본 자료를 자동 삭제한다.
6. **판례가 없으면 없다고 말한다.** 임계값을 넘는 검증된 판례가 없을 때 결과를 억지로 생성하지 않는다.

## 3. 대상 사용자

서비스는 양쪽 사용자를 지원하되 처음부터 흐름을 분리한다.

### 3.1 피해를 받은 사람

- 받은 메시지, 이미지, 음향 등의 상황을 입력한다.
- 자신이 겪은 상황과 사실관계가 비슷한 공개 판례를 확인한다.
- 서비스는 신고 가능 여부나 신고 절차를 안내하지 않는다.

### 3.2 신고를 받았거나 경찰 연락을 받은 사람

- 자신이 전송한 내용과 대화 경위를 입력한다.
- 사실관계가 비슷한 공개 판례를 확인한다.
- 서비스는 무죄 가능성, 수사 대응법, 진술 방향을 제시하지 않는다.

두 역할은 같은 판례 데이터와 검색 엔진을 사용하지만 질문 문구와 사례 요약의 관점을 분리한다. 어느 쪽에도 유리한 결과를 만들도록 점수를 조정하지 않는다.

## 4. MVP 범위

### 포함

- 비회원·일회성 분석
- 피해자 또는 피신고인 역할 선택
- 자유 서술 입력
- 카카오톡, SNS DM, 게임 채팅 등 이미지 첨부
- OCR을 통한 캡처 텍스트 추출
- 검색에 필요한 부족한 사실 최대 3개 추가 질문
- 개인정보 가림과 중립적 사실 요약
- 선별된 통신매체이용음란 판례 30~50건 검색
- 의미 유사도와 구조화 태그를 결합한 혼합 검색
- 상위 3~5개 판례 결과
- 사실관계 유사도, 닮은 점, 다른 점, 핵심 요약
- 공식 판례 원문 링크
- 브라우저 인쇄 기능을 이용한 PDF 결과 저장
- 원본 자료 자동 삭제

### 제외

- 고소·신고 가능 여부 판단
- 고소장, 진술서, 의견서 작성
- 경찰·검찰·법원 절차 안내
- 형량 및 처벌 예측
- 변호사 연결과 사건 의뢰
- 회원 계정과 사건 이력 저장
- 공개 베타 또는 불특정 다수 대상 출시
- 법원 판결서 인터넷열람의 무단 크롤링

법률 전문가 감수 전에는 가상 사례 또는 공개 판례에서 재구성한 사례를 사용하는 5~10명 규모의 비공개 테스트로 제한한다.

## 5. 사용자 흐름

1. 사용자는 홈 화면에서 자신의 역할을 선택한다.
2. 사건을 자유롭게 작성하고 필요하면 대화 캡처를 첨부한다.
3. 시스템은 OCR 결과를 보여주고 인식이 불확실한 부분을 사용자가 수정하도록 한다.
4. 시스템은 이름, 계정명, 전화번호 등 검색에 불필요한 개인정보를 가린다.
5. 시스템은 사건을 구조화하고 부족한 핵심 사실이 있으면 최대 3개의 질문을 한다.
6. 사용자가 구조화된 사건 요약을 확인한다.
7. 검색 엔진이 검증된 판례 데이터에서 후보를 찾고 유사도를 계산한다.
8. 출처 검증기를 통과한 판례만 결과 화면에 표시한다.
9. 사용자는 판례의 닮은 점, 다른 점, 핵심 요약과 공식 원문을 확인한다.
10. 결과를 브라우저에 전달한 뒤 원본 입력, 캡처, OCR 텍스트, 구조화된 사용자 사례를 삭제한다. 삭제 작업은 장애 상황에서도 1시간 안에 완료되어야 한다.

## 6. 화면 설계

참고 디자인의 흰 배경, 넓은 여백, 얇은 테두리, 보라색 그라데이션, 중앙 집중형 입력창을 제품의 기본 시각 언어로 사용한다.

### 6.1 홈 화면

- 왼쪽의 최소화된 세로 내비게이션
- 중앙의 보라색 시각 요소와 핵심 문구
- 피해자·피신고인 역할 선택
- 큰 자유 서술 입력창
- 대화 캡처 첨부 버튼
- “원본은 분석 후 자동 삭제” 안내
- “법적 판단이 아닌 사실관계 유사도” 고지
- 대표적인 입력 예시 카드

### 6.2 결과 화면

- 사용자가 확인한 중립적 사례 요약
- 검색한 데이터 출처와 판례 수
- 사실관계 유사도와 계산 기준
- 각 판례의 법원, 사건번호, 선고일
- 닮은 점과 다른 점
- 판례에서 중요하게 본 부분
- 요약의 근거 문단
- 공식 원문 열기 버튼
- 유사도가 법적 가능성을 의미하지 않는다는 상단 고지

화면에서 “성립 확률”, “고소 확률”, “유죄 확률”이라는 표현은 금지한다. 숫자는 항상 “사실관계 유사도”로 표시한다.

## 7. 시스템 구성

각 구성요소는 하나의 책임만 갖고 명확한 입력과 출력을 사용한다.

### 7.1 입력 세션 관리자

- 역할, 자유 서술, 추가 질문 답변을 임시 세션에 보관한다.
- 회원 계정이나 영구 사건 기록을 만들지 않는다.
- 분석 완료, 사용자 취소, 1시간 TTL 중 가장 먼저 발생한 시점에 삭제를 요청한다.

### 7.2 임시 업로드 저장소

- 이미지 파일을 암호화된 임시 영역에 보관한다.
- 파일 크기와 형식을 제한하고 악성 파일을 거부한다.
- 애플리케이션 로그에 이미지 경로나 원문 내용을 기록하지 않는다.

### 7.3 OCR 및 개인정보 가림기

- 캡처에서 텍스트를 추출한다.
- 낮은 신뢰도의 문장은 사용자가 확인하게 한다.
- 이름, 계정명, 전화번호, 이메일, 주소 등 검색에 불필요한 정보를 가린다.
- 개인정보 가림이 끝난 텍스트만 다음 단계로 전달한다.

### 7.4 사실 구조화기

자유 서술과 OCR 텍스트를 다음 구조로 변환한다.

- 사용자 역할
- 전달 매체
- 메시지 또는 게시물의 형태
- 상대방 특정 방식
- 실제 도달 또는 인식 가능한 상태
- 당사자 관계
- 대화·다툼의 경위
- 표현 유형
- 반복 여부
- 다른 경로를 통한 추가 전송 여부

구조화 결과에는 유죄, 무죄, 성립, 불성립 등의 판단 필드를 두지 않는다.

### 7.5 판례 저장소

판례 한 건은 최소한 다음 필드를 가진다.

- 내부 판례 ID
- 데이터 제공기관의 원본 ID
- 법원명
- 사건번호
- 사건명
- 선고일
- 공식 원문 URL
- 원문 텍스트
- 원문 해시
- 수집일과 마지막 검증일
- 구조화 사실 태그
- 검색 임베딩
- 원문 문단 ID

법원명, 사건번호, 선고일, 공식 URL, 원문 텍스트 중 하나라도 없으면 검색 가능 상태로 전환하지 않는다.

### 7.6 데이터 소스 어댑터

데이터 제공기관마다 별도 어댑터를 둔다. 검색·요약 계층은 어댑터의 내부 구현을 알 필요가 없다.

- `CuratedPrecedentSource`: 관리자가 검증한 30~50건
- `LawOpenDataSource`: 국가법령정보센터 판례 목록·본문 API
- `CourtJudgmentSource`: 법원 판결서 인터넷열람 연계가 적법하고 기술적으로 가능해진 뒤 추가
- `VerifiedManualSource`: 합법적으로 확보한 판결서를 관리자가 검증해 추가

### 7.7 혼합 검색기

초기 유사도는 다음 요소를 결합한다.

- 45%: 중립적 사건 요약의 의미 유사도
- 45%: 구조화 사실 태그 유사도
- 10%: 판례가 다룬 쟁점의 중복도

구조화 사실 태그는 전달 매체, 당사자 관계, 사건 경위, 도달 방식, 표현 유형, 반복 여부를 포함한다. 판결 결과와 형량은 유사도 계산에 사용하지 않는다.

초기 표시 기준은 다음과 같다.

- 최상위 점수가 55 미만이면 “현재 데이터에서 확인된 유사 판례가 없습니다”를 반환한다.
- 55 이상인 판례 중 상위 3개를 기본 표시하고 최대 5개까지 확장한다.
- 점수는 현재 검색 데이터 안에서의 비교값이며 전체 법원 판결을 대표하지 않는다.

가중치와 임계값은 고정 테스트 세트의 검색 품질을 기준으로 조정하되 법적 결과에 맞추어 조정하지 않는다.

### 7.8 출처 검증기

출처 검증은 판례 표시 전의 강제 단계다.

1. 검색 결과의 내부 ID가 판례 저장소에 존재하는지 확인한다.
2. 법원명, 사건번호, 선고일이 저장된 원문 메타데이터와 일치하는지 확인한다.
3. 공식 URL이 허용 도메인인지 확인하고, 24시간 이내에 성공한 링크 상태 검사 기록이 있는지 확인한다.
4. 저장된 원문 텍스트의 현재 해시가 수집·검증 시 기록한 원문 해시와 일치하는지 확인한다.
5. 검증을 통과한 내부 ID만 결과 조립기로 전달한다.

언어 모델은 사건번호나 공식 URL을 생성할 권한이 없다. 결과 조립기는 언어 모델의 자유 텍스트가 아니라 검증된 저장소 필드에서 사건번호와 URL을 읽는다. 어느 검증 단계에서든 불일치가 생기면 안전 실패 방식으로 해당 판례를 표시하지 않는다.

### 7.9 근거 기반 요약기

- 검증된 한 판례의 원문만 입력으로 받는다.
- 판시사항, 판결요지, 판단 이유에서 필요한 부분을 선택한다.
- 각 요약 문장에 원문 문단 ID를 붙인다.
- 근거 문단이 없는 문장은 제거한다.
- 요약 검증에 실패하면 요약 없이 원문 링크만 제공한다.
- 서로 다른 판례의 내용을 하나의 요약에 섞지 않는다.

### 7.10 결과 조립기

- 검증된 판례 메타데이터
- 유사도 점수
- 닮은 점과 다른 점
- 근거가 연결된 요약
- 공식 원문 링크
- 검색한 데이터 출처와 판례 수

위 정보만 화면에 전달한다. 검증된 판례가 없으면 빈 결과 상태를 반환한다.

## 8. 데이터 구축 계획

### 8.1 1단계: 선별 판례 데이터

- 국가법령정보센터에서 통신매체이용음란 관련 대법원 및 공개 하급심 판례 30~50건을 선별한다.
- 사건번호, 선고일, 법원, 원문 URL을 사람이 확인한다.
- 사실관계 태그와 원문 문단 ID를 만든다.
- 판례별 검색 예시를 작성해 회귀 테스트에 사용한다.

### 8.2 2단계: 국가법령정보센터 API

- 판례 목록 API로 신규 후보를 가져온다.
- 판례 본문 API로 원문과 메타데이터를 수집한다.
- 새 데이터는 자동 공개하지 않고 출처 검증을 통과한 뒤 검색 색인에 포함한다.
- 삭제·변경 데이터와 공식 URL 상태를 주기적으로 확인한다.
- 화면에 데이터 제공기관과 마지막 업데이트 날짜를 표시한다.

관련 공식 자료:

- [국가법령정보 공동활용 판례 API](https://open.law.go.kr/LSO/openApi/guideList.do)
- [공동활용 이용 및 출처 정책](https://open.law.go.kr/LSO/information/guide.do)
- [공공데이터포털 판례 본문 API](https://www.data.go.kr/data/15057123/openapi.do)

### 8.3 3단계: 법원 판결서 인터넷열람 확장

법원 판결서 인터넷열람은 국가법령정보센터의 주요 판례보다 넓은 범위의 판결서를 제공할 수 있지만, 일부 사건은 공개가 제한되고 건별 열람 수수료가 있으며 모든 판결을 일괄 제공하는 공개 API로 가정할 수 없다.

따라서 다음 순서로만 확장한다.

1. 서비스 이용조건, 수수료, 비실명 처리, 재이용 가능 범위를 문서로 조사한다.
2. 법원 또는 관련 기관에 자동 연계, 대량 이용, 서비스 내 요약·링크 제공 가능 여부를 문의한다.
3. 공식 API, 데이터 제공 계약 또는 명시적 허가가 확인되기 전에는 자동 수집기를 구현하지 않는다.
4. 허가된 방식이 생기면 `CourtJudgmentSource` 어댑터를 구현한다.
5. 공식 연계가 불가능하면 합법적으로 확보한 판결서를 관리자가 개별 검증해 추가하는 `VerifiedManualSource`만 사용한다.
6. 법원 판결서도 동일한 사건번호·선고일·법원·원문·해시 검증을 통과해야 한다.
7. 결과 화면에 데이터 출처별 판례 수를 구분해 표시한다.

관련 공식 자료:

- [법원 판결서 인터넷열람 제도](https://patent.scourt.go.kr/common/wcd/wcd_desc.jsp)
- [법원 판결서 인터넷열람 서비스 안내](https://www.scourt.go.kr/portal/information/finalruling/guide/guide_02.jsp)
- [판결서 열람 제한 안내](https://www.scourt.go.kr/portal/information/finalruling/guide/guide_01.jsp)

## 9. 개인정보와 보안

- 회원가입 없이 난수 세션 ID를 사용한다.
- 업로드 원본은 암호화된 임시 저장소에만 둔다.
- 개인정보 가림 전 원문을 판례 검색, 임베딩, 분석 로그에 사용하지 않는다.
- 외부 AI 서비스를 사용한다면 학습 사용 금지와 최소 보관 설정을 지원하는 구성을 선택한다.
- 결과 생성 직후 원본 삭제를 요청한다.
- 삭제 작업 장애 시 재시도하고 1시간 TTL이 지난 자료는 별도 정리 작업이 강제 삭제한다.
- 운영 로그에는 세션 내용 대신 오류 코드, 처리 시간, 파일 크기 범주 등 비식별 정보만 기록한다.
- 결과 데이터는 응답을 전달하는 동안에만 처리하고 서버 데이터베이스에 저장하지 않는다.
- 사용자가 브라우저 인쇄 기능으로 PDF를 저장하더라도 서버에는 결과 파일을 보관하지 않는다.

## 10. 오류 처리

### OCR 신뢰도가 낮음

추출 문장을 사용자에게 보여주고 확인되기 전까지 검색하지 않는다.

### 핵심 사실이 부족함

최대 3개의 추가 질문을 한다. 그래도 핵심 사실이 부족하면 검색을 실행하지 않고, 비교에 필요한 정보가 부족하다는 빈 상태를 보여준다.

### 유사 판례가 없음

빈 결과 화면과 현재 검색 범위를 보여준다. 판례를 생성하거나 점수를 올리지 않는다.

### 공식 URL 또는 메타데이터 검증 실패

해당 판례를 결과에서 제외한다. 모든 후보가 실패하면 빈 결과를 반환한다.

### 요약 근거 연결 실패

AI 요약을 숨기고 검증된 메타데이터와 공식 원문 링크만 제공한다.

### 공식 API 장애

마지막으로 검증된 로컬 판례 색인을 읽기 전용으로 사용하고 데이터 기준일을 표시한다.

### 원본 삭제 실패

결과 화면에는 삭제 재시도 중임을 알리고 운영 경고를 생성한다. 백그라운드 삭제 작업이 1시간 TTL 안에 강제 삭제한다.

## 11. 테스트 계획

### 단위 테스트

- 역할별 입력 구조화
- 개인정보 가림
- 유사도 가중치와 임계값
- 결과 상위 K개 정렬
- 검증 실패 판례 제외
- 요약 문장별 문단 ID 강제
- 원본 삭제와 TTL

### 판례 환각 방지 테스트

- 존재하지 않는 사건번호를 모델 입력에 섞어도 결과가 생성되지 않아야 한다.
- 저장소에 없는 사건번호와 URL은 결과 조립기가 거부해야 한다.
- 판례 A의 메타데이터에 판례 B의 본문이 연결되면 해시·메타데이터 검증이 실패해야 한다.
- 공식 링크가 끊기면 해당 판례를 숨겨야 한다.
- 요약의 모든 문장에 동일 판례의 원문 문단 ID가 있어야 한다.

### 검색 품질 테스트

- 공개 판례를 바탕으로 만든 가상 사례 20~30개와 기대 판례를 고정 테스트 세트로 만든다.
- 테스트 사례의 90% 이상에서 기대 판례가 상위 3개 안에 포함되는 것을 프로토타입 목표로 삼는다.
- 같은 입력을 반복했을 때 순위와 점수가 허용 범위 안에서 유지되어야 한다.
- 판결 결과를 제거해도 검색 순위가 유지되는지 확인한다.

이 평가는 법적 정답을 검증하는 것이 아니라 검색 엔진이 알려진 공개 판례를 안정적으로 다시 찾는지를 검증한다.

### 개인정보 테스트

- 로그에 원문이나 개인정보가 남지 않는지 검사한다.
- 분석 완료 후 원본 파일이 삭제되는지 확인한다.
- 장애를 강제로 발생시켜도 1시간 안에 삭제되는지 확인한다.

### 사용자 이해도 테스트

5~10명의 테스트 참가자에게 가상 사례를 제공하고 다음을 확인한다.

- 참가자의 80% 이상이 유사도를 법적 가능성과 구분한다.
- 참가자의 80% 이상이 닮은 점과 다른 점을 설명할 수 있다.
- 모든 참가자가 공식 원문 버튼을 찾을 수 있다.
- 참가자가 결과 화면을 실제 법률 자문으로 오인하는 표현을 발견하면 수정한다.

## 12. 프로토타입 성공 기준

- 화면에 표시된 판례의 100%가 내부 검증 레코드와 공식 원문 URL을 가진다.
- 언어 모델이 생성한 사건번호가 화면에 표시되는 경우는 0건이다.
- 표시된 요약 문장의 100%가 같은 판례의 원문 문단과 연결된다.
- 고정 검색 테스트의 90% 이상에서 기대 판례가 상위 3개 안에 포함된다.
- 원본 업로드의 100%가 분석 완료 즉시 삭제 요청되고, 늦어도 1시간 안에 삭제된다.
- 테스트 참가자의 80% 이상이 사실관계 유사도와 법적 가능성을 구분한다.

## 13. 공개 출시 전 필수 조건

현재 프로토타입에는 법률 전문가 감수가 없다. 다음 조건을 충족하기 전에는 실제 사건 사용자를 대상으로 공개하지 않는다.

- 통신매체이용음란 판례 태그와 요약에 대한 변호사 또는 법률 전문가 검수
- 서비스 문구와 면책·고지 문구 검수
- 개인정보 처리방침과 삭제 절차 검토
- 판례 데이터 이용조건과 출처 표시 검토
- 검색 품질 및 환각 방지 테스트 통과
- 보안 점검과 파일 업로드 공격 테스트 통과

## 14. 향후 범위

법률 전문가 검수와 판례 탐색 기능의 신뢰성이 확보된 뒤에만 신고 절차 안내, 조사 절차 안내, 문서 작성, 전문가 연결을 별도 프로젝트로 검토한다. 이 기능들은 현재 MVP에 포함하지 않으며 각각 독립적인 설계와 검수 절차를 거친다.
